# ADR 0020 — Knowledge Basket object storage

**Status:** accepted
**Date:** 2026-09-08
**Related:** ADR 0002 (denormalised `org_id`), ADR 0010 (ACL principals), ADR 0011
(retrieval ACL), ADR 0012 (Postgres is the queue), ADR 0017 (Cloud Tasks doorbell)

## Context

The Knowledge Basket is a per-employee file workspace whose contents must become
searchable knowledge inside the KT console. Nothing in the deployment stores a byte of
user-uploaded content today, and the audit that preceded this decision established four
facts that shape every choice below.

**There is no object storage and no infrastructure-as-code.** `gcloud storage buckets
list` returns nothing; `infra/` contains only `docker/`; every cloud resource was created
by hand or by `.github/workflows/deploy.yml`. The storage APIs *are* enabled
(`storage.googleapis.com`, `storage-api`, `storage-component`), and so is
`iamcredentials.googleapis.com` — which matters more than it looks.

**There is no file-upload path anywhere.** No `UploadFile`, no multipart handler, no
`python-multipart` dependency, no signed-URL code, no storage client in any
`pyproject.toml`.

**There is exactly one text-extraction library in the whole workspace: `openpyxl`**, added
last release for bulk onboarding. No PDF reader, no DOCX reader, no PPTX reader, no OCR,
no speech-to-text.

**The ingestion pipeline already exists and must be reused rather than forked.**
`jutsu_worker.pipeline.persist_document(session, *, org_id, source_id, raw: RawDocument)`
versions a document by `content_hash`, writes its chunks and its ACL grants, and returns
an outcome of created / updated / unchanged. `RawDocument.body` is `str` — the pipeline
consumes **text**, not bytes.

## Decision

### One bucket, server-generated keys

A single regional bucket in `asia-south1`, matching Cloud Run and Cloud SQL. Uniform
bucket-level access, public access prevention enforced, versioning on.

**Not a bucket per tenant.** Buckets are a project-level resource with quotas and
per-bucket IAM; a bucket per organisation makes provisioning part of sign-up, makes IAM
the isolation mechanism, and caps the product at the project's bucket limit. Isolation
here is the same isolation everything else uses: a row in Postgres under `ENABLE` +
`FORCE` row-level security. The bucket is a byte store that is never consulted without a
database row that has already passed an RLS-scoped query.

**The object key is generated by the server and contains no user input:**

```
org/{org_id}/{file_id}
```

Both are UUIDs the server chose. The original filename is stored in a column and never
appears in a path. This is what makes path traversal, object-overwrite and
key-collision attacks unrepresentable rather than merely filtered — there is no input to
sanitise, because the input never reaches the key. `org_id` leads the key so a
misconfiguration is auditable by prefix, not because the prefix enforces anything.

### Signed URLs, minted by `signBlob` — never a service-account key

Uploads go **browser → GCS directly** under a V4 signed URL; downloads likewise. Two
reasons, and the first is decisive: Cloud Run caps a request body at 32 MiB, which a
video or a large deck exceeds, so proxying uploads through the API would make the
supported-format list a lie. The second is that a proxied upload spends API CPU and
memory for the duration of a client's slow connection.

**No private key exists anywhere.** `google-cloud-storage` signs V4 URLs through the IAM
Credentials API (`signBlob`) when the runtime service account holds
`roles/iam.serviceAccountTokenCreator` on itself. No key material is generated,
downloaded, stored in Secret Manager, or shipped in an image — which is the failure mode
that makes "signed URLs" a liability in most deployments. `iamcredentials.googleapis.com`
is already enabled.

The upload URL is pinned to the exact key, the declared content type, and a size ceiling
(`x-goog-content-length-range`), and expires in minutes. A signed URL is therefore a
capability for one object of one size of one type, not for the bucket.

### Validation happens after the bytes land, and before anything reads them

The direct-to-GCS trade is that the API cannot inspect content on the way past. So the
lifecycle has an explicit gate:

```
UPLOADING → UPLOADED → VALIDATING → EXTRACTING → CHUNKING → EMBEDDING → READY
                          ↓             ↓            ↓           ↓
                       REJECTED      FAILED       FAILED      FAILED
```

`POST /v1/basket/files/{id}/complete` re-reads the object's own metadata from GCS —
size and checksum, as GCS computed them, not as the client claimed — and refuses a
mismatch. The worker then **sniffs magic bytes** and refuses a file whose real type
disagrees with its declared one. Content-type spoofing is caught by reading the content;
a declared type is treated as a hint for the signed URL and as nothing else.

An object that never reaches `UPLOADED` is garbage the lifecycle rule removes.

### What "supported" honestly means

The pipeline consumes text. A format is **searchable** only if there is a real extraction
path to text; everything else is **stored** — kept, listed, downloadable, previewable
where the browser can — and says so in the UI rather than pretending.

| Format | Status | How |
| --- | --- | --- |
| TXT, MD, CSV | searchable | decoded directly |
| XLSX, XLSM | searchable | `openpyxl`, already vendored and already bounded against zip bombs |
| PDF | searchable | `pypdf` (new dependency, pure Python) |
| DOCX | searchable | `python-docx` (new dependency, pure Python) |
| PPTX | searchable | `python-pptx` (new dependency, pure Python) |
| PNG, JPEG, GIF, WEBP | **stored only** | no OCR in the stack; adding Tesseract means a system binary in the image |
| MP4, MOV, WEBM, MP3, WAV, M4A | **stored only** | no speech-to-text in the stack |
| DOC, PPT, XLS (pre-2007 binary) | **stored only** | the pure-Python readers do not read them; LibreOffice in the image is a different decision |
| ZIP | **stored only, never extracted** | see below |

**ZIP is deliberately not extracted.** Safe extraction needs bounds on entry count,
uncompressed size, nesting depth, and member paths, and each of those is a place to be
wrong — with the payoff being files the employee could have uploaded individually. The
archive is stored and downloadable; its contents are not indexed. The bulk-onboarding
work already demonstrates the failure mode: `MAX_XLSX_BYTES` bounded the *compressed*
archive and a one-megabyte file could still declare a gigabyte.

### One source row per organisation, one document per file

The basket is a `sources` row with a new `source_system` value, `basket`, added the way
migration 0017 added `zoom`. Each file that yields text becomes a `RawDocument` and goes
through `persist_document`, so it is versioned, chunked, embedded, ACL-granted and
searchable by exactly the machinery every connector uses. No parallel knowledge system,
no second retrieval path, no second ACL model.

Grants are minted through `owner_acl` — the only grant-minting path in the codebase — so
an uploaded file is visible to its uploader's principal and to nobody else until an
explicit sharing decision exists. That decision is not in this ADR.

## Consequences

**The employee never waits for processing.** `complete` returns as soon as the object is
verified; extraction, chunking and embedding are durable jobs on the existing queue, and
the UI shows the real state rather than a spinner that lies.

**A file can be stored and not searchable, and the product says so.** That is the honest
consequence of having no OCR and no ASR, and it is visible in the interface rather than
buried.

**Three new pure-Python dependencies.** `pypdf`, `python-docx` and `python-pptx` are
parsers reading untrusted input, which is a real attack surface — each is bounded by size
and page/slide/paragraph count before parsing, and each runs in the worker rather than in
the API.

**A bucket and two IAM bindings must exist before the feature works.** They are created
outside Terraform because there is no Terraform; the commands are recorded in
`docs/deploy.md` so the resource is reproducible, and the API refuses to start with a
half-configured storage environment rather than failing per-request.

## Rejected alternatives

**Proxying uploads through the API.** Simplest, and it would let content be sniffed before
storage — but Cloud Run's 32 MiB request cap makes the format list dishonest, and a slow
client would hold API capacity.

**A service-account JSON key for signing.** The conventional way to sign URLs, and it puts
a private key in Secret Manager and in the container's memory. `signBlob` removes the key
entirely.

**Storing bytes in Postgres.** Viable for text at this scale and indefensible for video.
It also puts multi-megabyte blobs in the same instance the request path depends on.

**Extracting ZIP archives.** Rejected above: bounded gain, four new ways to be wrong.

**A separate `basket_chunks` table with its own search path.** This is the one that would
have been quietest and worst — a second retrieval path is a second ACL predicate, and
ADR 0011 exists because a second predicate is how revocation stops working.
